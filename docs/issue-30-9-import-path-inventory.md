## Shared Behavior To Standardize

- One import policy should name the canonical staged path for asset creation: parse, validate, preview/report, commit, and clear/exit.
- Asset identity normalization should be consistent: trim and uppercase `asset_tag`; specify whether barcode fallback is allowed outside network CSV.
- Duplicate checks should be consistent before writes: in-file asset tags, in-file serials where serial participates, existing asset tags, existing serials, and slot occupancy.
- Every DB-writing import should have an explicit all-or-nothing transaction boundary and a documented rollback expectation.
- UI import routes should consistently require admin role for reference and bulk-create actions; CLI imports need an explicit operating boundary because Flask role checks do not apply.
- Audit/event expectations need one rule: asset imports should either use the shared committer or explicitly append equivalent creation and slot events.
- Preview/report semantics should be named consistently. Some paths have interactive preview, some have validation reports, and some only stop on exception.

## Entity-Specific Rules To Keep Distinct

- Laptop, Switch, and Router are all valid AssetTrack equipment types for general asset intake and standard XLSX inventory import.
- Network CSV is intentionally Switch/Router only and rejects CMDB/network-configuration fields.
- Holder import uses email as its match key; asset import uses asset tag. These should not be merged.
- Organization and building names are reference data with case-insensitive uniqueness; they are not custody truth and must not rewrite event or receipt history.
- Slot provisioning creates empty storage capacity. It should not append custody events until an asset is assigned or moved.
- Existing slot assignment rules must keep case and slot paired; partial case/slot values should remain invalid unless a future issue decides otherwise.

## Unresolved Questions

- Should generic ingest CLI remain a supported operational entry point, or should it be treated as an internal helper?
- Should the network admin page stay template-only, or should it own upload, preview, and commit for switch/router CSVs?
- Should holder import receive an explicit preview/confirmation step before mutating holders and organizations?
- Should standard XLSX inventory import move through `commit_batch`, or keep a separate importer with documented event equivalence?
- What is the policy for serial-number uniqueness across all asset import paths?
- Should any import create or update `Building`, `Room`, `Case`, or `Slot` records automatically, or only reference pre-seeded records?
- Should CLI imports record an operator/user id linked to app users, or is a string actor acceptable?
- Should `tools/import_bq26_inventory.py` be retired, blocked, or preserved only as historical code?
